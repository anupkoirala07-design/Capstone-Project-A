# Week 4 – Business Rules

**Project:** Secure Retail – Product Catalogue System

Business rules describe how data must behave. Each rule is linked to the entities it affects and to where it is enforced:

- **DB** – a database constraint (NOT NULL, UNIQUE, CHECK, FOREIGN KEY).
- **API** – backend validation logic.
- **Both** – enforced in both places.

The frontend may repeat these checks for a better user experience, but the backend is always the final authority.

## Accounts and security

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-01 | Each user must have a unique email address. Emails are stored in lower case. | USERS | Both |
| BR-02 | Passwords must be at least 8 characters and include a letter and a number. Only a bcrypt hash is stored; plain-text passwords are never saved or logged. | USERS | API |
| BR-03 | A user's role is either Customer or Admin. Only Admins can create, update or deactivate categories, brands, products, variants, images and inventory. | USERS | API |
| BR-04 | A user with orders cannot be deleted. The account is deactivated (`IsActive = FALSE`) instead. | USERS, ORDERS | Both |
| BR-05 | A user can save many addresses, but only one can be the default. | ADDRESSES | API |
| BR-06 | Customers can only view and change their own addresses, cart, wishlist, orders and reviews. | ADDRESSES, CARTS, WISHLIST_ITEMS, ORDERS, REVIEWS | API |

## Product catalogue

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-07 | Every product belongs to exactly one category and one brand. | PRODUCTS, CATEGORIES, BRANDS | DB |
| BR-08 | A product must have at least one active variant before it is shown to customers. | PRODUCTS, PRODUCT_VARIANTS | API |
| BR-09 | Every variant has a unique SKU. | PRODUCT_VARIANTS | DB |
| BR-10 | Price must be greater than 0. A promotional price must be lower than the normal price and needs both a start and end date, with the end date on or after the start date. The promotional price is shown only between those dates. | PRODUCT_VARIANTS | Both |
| BR-11 | Every active product must have exactly one primary image, and every image must have alt text. | PRODUCT_IMAGES | API |
| BR-12 | Categories, brands, products and variants that are linked to other records are deactivated, not deleted. | CATEGORIES, BRANDS, PRODUCTS, PRODUCT_VARIANTS | Both |

## Inventory

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-13 | Each variant has exactly one inventory record, created at the same time as the variant. | INVENTORY, PRODUCT_VARIANTS | Both |
| BR-14 | Quantity on hand can never be negative. | INVENTORY | DB |
| BR-15 | Stock is reduced when a payment succeeds and restored if the order is cancelled. | INVENTORY, ORDERS, PAYMENTS | API |
| BR-16 | A low-stock alert is raised for admins when quantity on hand is at or below the low-stock threshold. | INVENTORY | API |
| BR-17 | A variant with zero stock is shown as "Out of stock" and cannot be added to a cart. | INVENTORY, CART_ITEMS | API |

## Cart and wishlist

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-18 | Each user has at most one cart, created the first time they add an item. | CARTS | DB |
| BR-19 | A variant appears only once in a cart. Adding it again increases the quantity. | CART_ITEMS | DB |
| BR-20 | Cart quantity must be at least 1 and cannot exceed the stock available or the variant's purchase limit. | CART_ITEMS, INVENTORY, PRODUCT_VARIANTS | API |
| BR-21 | A product appears only once in a user's wishlist. | WISHLIST_ITEMS | DB |

## Orders and payments

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-22 | An order must contain at least one order item. | ORDERS, ORDER_ITEMS | API |
| BR-23 | The unit price is copied from the variant at checkout (the promotional price if a promotion is active). Later price changes do not affect existing orders. | ORDER_ITEMS | API |
| BR-24 | Subtotal, delivery cost and total are calculated by the server. Prices or totals sent from the browser are ignored. | ORDERS, ORDER_ITEMS | API |
| BR-25 | Delivery orders must have an address. Click & Collect orders have no address and a delivery cost of $0. | ORDERS, ADDRESSES | Both |
| BR-26 | Order status only moves forward: Pending → Paid → Shipped → Delivered. An order can be Cancelled only while it is Pending or Paid. | ORDERS | API |
| BR-27 | A tracking number is required when an order is marked as Shipped. | ORDERS | API |
| BR-28 | Every order has a unique order number generated by the system. | ORDERS | DB |
| BR-29 | An order can have several payment attempts but only one successful payment. The order becomes Paid when a successful payment equals the order total. | PAYMENTS, ORDERS | API |
| BR-30 | Card numbers and security codes are never stored. Only the payment gateway's transaction reference is saved. | PAYMENTS | API |
| BR-31 | The quantity of a variant in one order cannot exceed its purchase limit (e.g. "Limit 2 per customer"). | ORDER_ITEMS, PRODUCT_VARIANTS | API |

## Reviews

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-32 | Only signed-in users can write reviews, and each user can review a product only once. | REVIEWS | Both |
| BR-33 | A rating must be a whole number from 1 to 5. | REVIEWS | DB |
| BR-34 | "Verified purchase" is set by the system when the user has a Delivered order containing any variant of the product. Users cannot set it. | REVIEWS, ORDERS, ORDER_ITEMS | API |
| BR-35 | New reviews start as Pending and are shown only after an Admin approves them. A product's average rating and review count are calculated from approved reviews, not stored. | REVIEWS | API |

## Enquiries

| ID | Rule | Entities | Enforced by |
|---|---|---|---|
| BR-36 | Guests and signed-in users can submit enquiries. Name, email, subject and message are required. | ENQUIRIES | Both |
| BR-37 | Messages are limited to 2,000 characters and HTML is removed before saving, to prevent cross-site scripting (XSS). | ENQUIRIES | API |
| BR-38 | Only Admins can view enquiries and change their status. | ENQUIRIES, USERS | API |

## Traceability to Week 2 risks

These rules address the data quality risks identified in the Week 2 Data Quality & Risk Analysis:

| Week 2 risk | Business rule(s) |
|---|---|
| Incorrect product price | BR-10, BR-23 |
| Discount higher than price or never expires | BR-10 |
| Stock not updated after a sale | BR-14, BR-15 |
| Wrong category assigned | BR-07 |
| Missing or broken product image | BR-11 |
| Duplicate product IDs | Primary keys on every table |
| Zero, negative or unrealistic cart quantity | BR-20 |
| Cart total manipulated on the client side | BR-24 |
| Invalid customer email | BR-01, BR-36 |
| Spam or malicious enquiry message | BR-37 |
| Weak or plain-text passwords | BR-02 |
| Fake or unapproved reviews shown | BR-34, BR-35 |
| Unauthorised access to personal data | BR-03, BR-06, BR-38 |
